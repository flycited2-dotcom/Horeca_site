## Находки

### Высокая важность

**1. Сервер перегружен, сайт периодически «замирает» на 8–10 секунд.**
Раздел «Нейтральное оборудование» из 17 замеров три раза отвечал 8–10 с вместо 0,9. С самого сервера (без сети) то же самое, при этом замирает даже TLS-рукопожатие (1,8 с), то есть тормозит сервер целиком. Память: свободно 180–240 МБ, своп занят на 2 ГБ из 4, часть MariaDB выгружена на диск (198 МБ), давление на диск и память по системным метрикам 7–10 %. Рядом работают чужие проекты (Next.js, Celery, Postgres, climat-simf.ru с прогревом кэша каждые 4 минуты). Гипотеза: рывки совпадают по времени с задачами соседних сайтов — не доказана. Магазин сам лёгкий: контейнеры занимают 37–225 МБ, на локальной копии раздел отвечает за 200 мс.

**2. Копия базы лежит только на том же сервере.**
Заявки, клиенты, ручные правки менеджеров, настройки — всё пропадёт вместе с сервером. Диск заполнен на 81 % (свободно 13 ГБ), сервер перезагружался 24.09, 27.09 и 30.09. Копию вне сервера заказчик отложил 01.10.2026 «до запуска», сайт запущен.

**3. Поиск не понимает словоформы и опечатки.**
Пусто по запросам «холодильники», «пароконвектоматы», «морозильники», «микроволновка», «посудомойка», «холодильнк», «хайколд». Работает: точное слово, артикул, неверная раскладка, часть названия. Покупатели пишут во множественном числе постоянно, это прямая потеря заявок. Время ответа поиска на боевом сайте 0,7–1,5 с.

### Средняя важность

**4. Известные уязвимости в `league/commonmark` 2.10.1** (одна «высокая» — замедление до отказа на таблицах, одна «средняя» — обход фильтра HTML). Практический риск низкий (Markdown вводит только администратор), но исправление уже есть: 2.10.3, проверено пробным обновлением.

**5. Мусор в каталоге виден покупателю и поисковикам.**
48 из 324 разделов пустые («0 моделей»), и все они в карте сайта: «Телевизор», «Утюг», «Холодильник», «АККР», «кхн», «Пресс для гамбургеров (не выбирать)», «не основной ассортимент». Описание у них — «… — 0 моделей в каталоге Гастроснаб». Для поисковиков это слабые страницы. Данные локальной копии: 90 товаров с «неликвид/не годен/тест» в названии, 146 названий длиннее 150 знаков, 18 групп дублей, 3 279 товаров без артикула. Пример мусорной карточки: «Контроль заполнения (Аппарат для мойки овощей)» с брендом «Завесы Юнигейт».

**6. Ошибка в описании товаров без цены: «цена цена по запросу, под заказ».**
Шаблон `shop.seo.product_description` содержит слово «цена», а подставляется «цена по запросу». Затронуты все товары по запросу (около 7 % каталога, ~1 000 штук). Исправление — одна строка.

**7. Главная медленнее остальных.**
Ответ 0,5–0,9 с, LCP 3,5 с, Lighthouse 88. Первые плитки на экране (`loading="lazy"`) загружаются с задержкой; нужно грузить первые 2–4 сразу.

**8. SEO-разметка неполная.**
Нет `rel="canonical"` на главной, в `/catalog`, `/brands` и `/wholesale`; у `Offer` нет срока действия цены и продавца, у `Organization` нет логотипа и структурного адреса, нет `WebSite` с поиском. Хлебные крошки (`BreadcrumbList`) на сайте есть, в микроразметке — в первой версии отчёта я это ошибочно назвал отсутствующим, проверив только JSON-LD.

**9. Заголовки безопасности и кэширование.**
Нет HSTS, CSP и Permissions-Policy. Каждому анониму (и каждому боту) на любой странице выдаётся сессия и `Cache-Control: no-store`: страницы нельзя кэшировать, не работает возврат «Назад» из кэша браузера (Lighthouse: bfcache). Redis ограничен 128 МБ с политикой `noeviction`, а по README сессии и кэш лежат в нём (фактический `.env` сервера не читал): при большом наплыве ботов память кончится, и записи начнут падать с ошибкой.

**10. Нет ограничения частоты** на «в корзину», «сравнить», «в избранное» и согласие на cookie. Бот может плодить корзины.

**11. Уведомления в Telegram иногда падают по таймауту.**
В журнале `queue-default` за 02.10 вечером — серия `SendTelegramMessage … FAIL` через 10 с; сервер достаёт `api.telegram.org` нестабильно. Письмо менеджерам остаётся второй дорожкой, но это единственная защита от «заявка не дошла».

**12. Процесс разработки.**
Нет автоматических проверок (CI): тесты, Pint и сборка запускаются вручную. Нет статического анализа. Ветка `main` — это спринт 0; боевой сайт собран из `feature/sprint-6-content`, шесть веток цепочкой не влиты. Если потерять компьютер разработки, останется один GitHub без «основной» ветки.

### Низкая важность

- Фото отдаются с чужого адреса `s3.spb.sprinthost.ru` (отдельное соединение, нет предварительного `preconnect`, бакет публичный целиком).
- «Габариты в упаковке 750*610*1015» выводятся как пришли от поставщика, без «×» и «мм» (правило §9 макетов).
- DMARC в режиме `p=none` (не блокирует подделку писем).
- Cookie-баннер занимает треть экрана телефона при первом визите.
- Яндекс Метрика передаёт хеш телефона (автоцели), а политика обещает «обезличенную статистику»; решение за заказчиком (HANDOFF, раздел 7, п. 24).
- Страница входа администратора на холодную открывается 2,8 с.
- Обновления: Laravel 13.32 → 13.34, Filament 5.8 → 5.9, Pest, Vite (без срочности).
- Учётные записи менеджеров не заведены, 2FA администратора пока не настроена; внешнего сторожа доступности нет; токен Telegram-бота нужно перевыпустить (он засветился в чате).
- Юридические страницы — черновики; уведомление Роскомнадзора пропущено решением заказчика. Риск остаётся на заказчике.
- Заголовок HANDOFF.md говорит «Обновлено 23.09.2026», хотя содержимое новее.

## Что не удалось проверить

- Боевая база: число упавших задач, заявок, лидов, учётные записи персонала, фактические пороги.
- `.env` на сервере: `APP_DEBUG`, драйверы кэша и сессий.
- Оформление заказа на боевом сайте (не отправлял, чтобы не создавать настоящих заявок и уведомлений).
- Админка вживую, телефоны заказчика, доставка писем до ящиков клиентов.
- Поведение под нагрузкой: проверял только лёгким потоком.
